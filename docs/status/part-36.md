## How a turn works now
- **A bubble** (`POST /characters/:id/bubbles`, `{requestId, text, quoteMessageId?}`) is stored the moment it is sent: an ordinary `messages` row plus a `web_turn_bubbles` row (idempotent per request id; a different body under the same id is `IDEMPOTENCY_CONFLICT`). Nothing is charged and no operation exists yet. The same text rules, access decisions (entitlement, points, trial counters, content gate, queue limits) as a single message are checked up front by a dry run of `WebAdmission` (`canAdmit`), so a bubble is accepted only if its turn could be admitted.
- **The turn** is ONE operation that answers the whole batch. The business object admits it (and charges it: one trial reply / points charge / daily-cap count) when the batch closes: the player has been quiet for **4 s** after the last bubble, or **5 bubbles** are waiting (closed inside the request that stored the fifth), and **no earlier turn of that conversation is still running**. A turn takes at most 5 bubbles (the oldest); at most 15 may wait (`WEB_TURN_BUBBLES_FULL`). `unknown` frees the slot (Part 54: its money stays held, nothing is resent).
- **Who triggers it:** the business object, not the open page. Cloudflare: the Durable Object's own alarm (`WebCloudExecutor` → `WebTurns.pass()` before the stage pass, `nextDue()` in its wake time; also in the no-external-calls branch of `business.ts`). Local Node server: a 250 ms timer. A reload, offline or a closed tab loses nothing: bubbles are rows.
- **The operation's input message is its LAST bubble**, so every table that keys one input message per operation (operations, snapshot, v7 request, attempts, dispatch ledger, publications) is unchanged. The earlier bubbles are found through `web_turn_bubbles.operation_id` (`turnMemberIds`; an operation with no bubble rows answers its own input, so every single-message request is byte-identical to before — `cast-off-main.json` and every snapshot test pass unedited).
- **Money / flow (Part 54, 43):** the turn goes through `WebAdmission.admit` exactly like a single message: one reservation for the turn's stages before the single generation call, budget reserved before every provider call, UNKNOWN never retried and its money held. Round trips stay ≤ 2 per reply (+ voice): tested on the production topology (`web-turns-36.integration`). Part 43's re-queue of provably-unsent replies runs unchanged on a turn of three bubbles (`web-requeue-batch-36.integration`: the whole Part 43 file, on a batched turn). If a turn cannot be admitted when its batch closes (e.g. the trial ran out meanwhile) its bubbles are marked `refused` with the code (never retried; the page shows 未发送); queue-full and the daily limit are transient and retried.
- **Page flow:** the composer is never blocked by a reply. The page sends bubbles one after another (in typed order) and follows the turn (`GET /characters/:id/turn`: `idle | collecting | replying | refused`); the header says 「正在讲话中」 only while `replying`. Bubbles sent meanwhile wait for the next turn.
- **Quote:** a bubble may quote any message of the SAME conversation (identity / world / conversation scoped; another conversation's or another player's id, or a missing one, is `QUOTE_UNAVAILABLE`, 404, and stores nothing). The writer's request carries it as `messages[].replyTo` (who wrote it, its text, delivery; read only from the same conversation; text cut at 500 characters); history carries `quote` (`text: null` = the original is gone: shown dimmed, no sentence). Tapping the quote scrolls to the original and flashes it once.
- **Storage:** no numbered migration. Two digest-checked runtime steps: `web_turn_*` (`web_turn_schema`, STOP **`WEB_TURN_SCHEMA_MISMATCH`**) and `web_feedback*` (`web_feedback_schema`, STOP **`WEB_FEEDBACK_SCHEMA_MISMATCH`**). Other new codes: `QUOTE_UNAVAILABLE` (404), `FEEDBACK_TARGET_INVALID` (400), `WEB_TURN_BUBBLES_FULL` (429); all in the refusal table.
- **Purges:** the turn rows and the ratings go with the world (account deletion, closed account, guest purge, both cleaners), with the conversation (player and owner deletion) and with the character; the lifecycle audit and the character-deletion audit now assert them (`turnsResidue`, `feedbackResidue`) and list the three tables.

## 👍 / 👎 and 语音反馈
- `POST /ratings` `{requestId, conversationId, messageId, rating: up|down|none, target?: voice|content}`: the desired state, so rate / switch / remove and a repeated request are idempotent; one rating per player per message; CSRF + Origin; only a reply (voice or text-fallback) published to THIS player in THIS conversation (anything else, another player's or conversation's message: `NOT_FOUND`). A 👎 carries `target` (a reply that came as text is `content` only). The writer (回复写法) and the model are copied when the rating is written; a switch clears the owner's 「已听」.
- **Admin 语音反馈** (owner only, desktop, under 运营): counts of 👍 / 👎 (and the 语音 / 内容 split) per character, per 回复写法 and per model over 7 / 30 / 90 天; the 👎 list newest first, filterable by character / 回复写法 / model and 未听, each item in the pseudonymous form of the transcripts (the review code `角色-XXXX`, nicknames replaced, emails / UUIDs / long hex scrubbed; her voice playable; the player's lines of the whole turn); 「已听」 (idempotent, audited by item number only); 导出 (Part 57, kind `feedback`, same columns + 评价 / 踩的是). Her plan (读到 / 目的) is a Part 58 field: Part 58 is not on this branch, so an item carries none yet. Hover tips only (docs/ADMIN_COPY.md); logs never contain content.

## Writer pins (changed on purpose)
- **No existing pin moves.** v7 and v8 prompts, protocols and policy hashes, `writerPins()`, `textPromptHash()` and every snapshot are untouched: a single message with no quote gets exactly the prompt it always did.
- **旧 (v7):** the batch is given in the form it already understands: `requiredMessageIds` lists every bubble (the prompt layer accepts up to 32; 审核对比 already used it) and `messages[].replyTo` carries a quote (`prompts/v7/text-content-rules.md` already explains it). No prompt change.
- **新 (v8):** when the turn has several bubbles or a quote, `WRITER_BATCH_NOTE` is appended LAST to the system message (`writer-v8.ts`; absent otherwise). Its sha256 is pinned: `72df760e9d483e9faf382259778d5d2f48114a3307701703d93fe9a0d49203fd` (asserted in `web-turn-request-36`). The words: answer once for the several bubbles in a row, skip the trivial, may bring up an earlier important one yourself, `replyTo` is a quote the server fixed (author / text), answer the quoted matter without repeating it. v8 marks every bubble of the turn covered by code (no "answer everything" tracking, no "later"). **Deploy order unchanged: generation before business** (an older generation Worker would omit the note; the batch would still be answered).
