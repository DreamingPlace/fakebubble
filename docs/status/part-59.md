# Part 59 — Admin: never lose edits, keep the scroll position, no freeze, per-item co-creation handling, relation reasons, offline characters, one 版本 control

Branch `part-59`. Before / after pictures: the artifact published in the session (not a branch). No migration 132: `expected-migrations` are byte-identical to main (56 inline + 56 R2, last 131 = `a6f581dd…990a`, checked with `node scripts/web-cloudflare-operator.ts expected-migrations`). No prompt text, policy or `castPromptHash` changed (see 「The cast view」).

## Causes (what was wrong)
1. **Lost edits.** Every admin save went through one transport that read the answer with `response.json()`. A Cloudflare challenge page (HTML), a network error and a 401 all ended as a generic failure; the page then went to the login screen (`run()` cleared `session` and the page's state on any 401) or simply forgot: nothing the owner typed was kept anywhere but in the page's DOM, and `adoptSession()` cleared the whole console when the CSRF token changed (a login in another tab, a re-verification), also resetting to 我的账号. 3 of 4 saves on 关系与故事 failed the same way: the challenge page appeared for each large POST.
2. **Logout for no clear reason.** The admin session was a **fixed 8 hours from sign-in** (`expires_at = created_at + 8 h`, never extended). An owner working past 8 hours, or a Cloudflare Access / cookie loss, ended in a logged-out console mid-edit. Also: an 11th sign-in revokes the oldest of one member's sessions (10 at most), and a different tab's login replaced the cookie.
3. **Scroll to the top.** The document (not a box inside the console) is the scroller. Pages empty themselves and refill (`replaceChildren`, a loading placeholder) while a click's request is in flight; while the page is shorter the browser clamps the scroll position to 0, and it stays there when the content returns. Reproduced on main with a 600 ms API delay on 关系与故事, 网络梗, 系统状态, 消耗表 and 管理员与权限 (position 72 → 0). `navigate()` also focused `.admin-content` without `preventScroll`.
4. **Freeze after switching tabs.** `window.focus` ran `refresh()` through the page-wide `run()`: it sets `busy`, and `render()` disables **every** button, input and select of the page (the 「not-allowed」 cursor) until the session read answers. The read had no deadline, so a hung answer (a challenge, a sleeping connection) froze the page for minutes. On main the browser check measured 359 disabled controls (21 before) and a click answered after 1.8 s.
5. **Co-creation handled per submission.** `adopt()` set the whole submission `processed` on the first adoption, and the console patched `status: 'processed'` locally and removed it from 新, hiding the items nobody had handled. 已处理 was ordered by sent time.

## What changed
### Session
`apps/server/invites/web-invite-admin.ts`: **idle timeout 8 h, sliding**; **absolute limit 24 h** after sign-in (kept for security); a renew is written at most every 10 minutes (`ADMIN_RENEW_STEP_MS`). Both `authorize` and `session` renew. The cookie stays a browser-session cookie. The console also asks for the session every 10 minutes while it is being used (pointer, key or scroll in the last 10 minutes) so a quiet owner (reading, typing a long text) is not idle. Part 55's server-side merge, CSRF and Origin checks are untouched.

### Never lose an edit
- `services/admin-connection.ts` + `invite-admin-api.ts`: an answer that is not the API's JSON (HTML challenge, any status), a network error, a timeout, an opaque redirect or a 401 `ADMIN_UNAUTHORIZED` of a console that is signed in is an **interruption** (`AdminInterruptedError`), not a failed save. One floating line (`#admin-conn`, `ui` text in docs/ADMIN_COPY.md) says so with 验证 / 重新登录, which opens the console in a popup (`#/reauth`; it closes itself once signed in) without leaving the page. The page probes the session every 4 s while interrupted (and on focus); the moment the API answers, the saves that registered for retry run again, once each.
- `features/admin/ui/edit-keeper.ts`: the owner's unsaved edits in `localStorage`, key `fb-admin-edits:v1:<page>:<character>:<section>:<revision>`; written while editing (300 ms) and on page hide; removed by a successful save, a deliberate 放弃 and **explicit sign-out** (a session that merely expired keeps them). Only the owner's own editor fields: no player data, no token, no session. Everything is guarded (private window, quota: nothing kept, nothing breaks). Entries older than 30 days are ignored.
- Wired into: 角色工作台 form (all sections; `characterForm.snapshot()` reads without the save checks), 说话档案 (`panelKeeper`), 关系与故事 (the working copy with its base), 网络梗 (the switch that could not be sent, with its request id), 共创收件箱 adopt boxes. **Restore** (「恢复未保存的修改」): the same draft revision → the copy as it was; a draft that moved on → only the fields the owner changed are laid over the current one (`overlayEdits`; 关系与故事 uses the Part 55 field merge, a field changed on both sides is named).
- Each of those editors registers its save for the automatic retry after an interruption (workbench, 说话档案, adopt box, cast, 网络梗, inbox adopt). Saves are idempotent as before (request ids; `requestFor` in the cast).
- **Largest save body**: a workbench profile save is limited to **259,583 bytes** (`PROFILE_BODY_LIMIT`); a cast save to **4,000,000 bytes** (the stored document is at most 1,900,000 bytes). 100 changed ratings in one cast save measured **28,869 bytes** on the fixture. A save still sends the whole draft (the server merges field by field, Part 55); "send what changed / chunk" was **not** built: the draft is one compare-and-swap document, so a chunked save would need a new protocol. What the owner lost was the edit, not the size; that is fixed (an interrupted save keeps everything and retries). Say if you want a delta protocol as its own Part.

### Scroll
`features/admin/ui/keep-scroll.ts`: one observer for the console remembers where the owner scrolled each scroller (the document and every inner box), ignores the browser's own clamp that follows a repaint, and puts the position back after the page changed, as far as the new content reaches. Opening another page (`navigate`) starts at the top. `.admin-content.focus({preventScroll:true})`.

### No freeze
`refresh()` (focus, visibilitychange, keep-alive) no longer runs through `run()`: nothing is disabled, nothing waits for it; the session read has a **15 s deadline**; an interruption only raises the connection line. A re-login of the SAME administrator only replaces the CSRF token (it used to clear the page and send it to 我的账号); a different administrator resets everything and removes the kept edits.

### 共创收件箱
- **Per item.** New code-installed table `web_cocreation_item_marks` (`apps/server/cocreation/web-cocreation-marks-schema.ts`; digest-checked like Part 39's tables, STOP code `WEB_COCREATION_MARKS_SCHEMA_MISMATCH`; **no numbered migration**; removed with the submission by the purge). An item is handled when it is adopted (`adopted_at`, as ever) or marked 不采纳 / 复制 / 标为已处理; the reason of a two-person note is an item too. `adopt()` no longer moves the submission: only the last unhandled item does. List rows and the detail carry `itemCount` / `handledCount`; new route `cocreation/mark-item`; the console shows 「已处理 x/n」 and re-reads the note from the server after every item action. 整条标为已处理 is the existing `set-status` (moves at once).
- **已处理** is ordered by `processed_at`, newest first, with its own cursor.
- **Relation reasons.** `cocreation/relation/adopt-reason` (needs cocreation.manage and cast.edit) writes the reason as the 关系注解 of that pair in the cast **draft** at its current revision, idempotent, never published, appended under an existing note of the pair, limit 200. Adopting the reason never adopts the story and vice versa; the note leaves 新 when both are handled.

### The cast view
A new optional document key `pairNotes` (`{id, a, b, text ≤ 200}`, ≤ 400, one per unordered pair; no migration, no schema bump, **absent when empty so every existing document keeps its bytes and digest**). It is validated, merges like any entry (Part 55), survives cast files, goes with a deleted character, and the compiled view of BOTH characters gets `relations[].note`. The prompt text, the policy and `castPromptHash` are unchanged; only a cast that has a note compiles to a view with that one extra key (none in production yet). CAST_CONTEXT_ENABLED is on in production, so it reaches the characters' prompts as soon as a note is adopted and published.

### Offline characters
角色工作台 rail, 共创收件箱 (chips and notes) and 关系与故事 (grid and pickers) hide characters that are not live (not launched yet, or delisted); **显示未上线** shows them. The one being looked at is never hidden. The cast document is never filtered: offline characters round-trip on save byte for byte (checked).

### 版本
关系与故事: the version bars above the content are gone. One 「版本」 button in the title row opens a panel over the page (draft number, the list with 恢复此版本, 从旧资料导入, 导出文件).

## Limits
- The popup flow needs the browser to allow `window.open`; otherwise a new tab opens.
- The automatic retry covers the editors listed above; a one-click action elsewhere (e.g. 广播 send) is not retried: it shows the connection line and the owner repeats it (those calls are not idempotent drafts).
