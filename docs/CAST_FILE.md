# 阵容文件（cast file）— 写给 Codex

一份 JSON 文件，一次写完所有角色的阵容内容：身份、说话方式、经历、关系评分、称呼与相处、组合、故事、梗。
管理员在 **关系与故事 → 导入文件** 里导入，**只进入草稿**，不会发布，也不会碰玩家的任何数据。

```
node scripts/cast-file.ts validate <你的文件>
```

退出码 `0` 才表示：**能导入，也能发布**。先把它跑到 `0` 再交给管理员。示例：`examples/cast-file.example.json`（3 个角色，其中 1 个新角色；2 个人物；1 个组合；2 个故事）。

## 1. 文件长什么样

```jsonc
{
  "format": "burbur-cast",     // 固定
  "version": 1,                // 固定
  "schema": 1,                 // 固定
  "world": { "background": "…" },
  "characters": [ … ],         // 聊天角色，最多 15 个
  "people": [ … ],             // 不是聊天角色的人，最多 40 个
  "ratings": { "甲的编号": { "乙的编号": 4.5 } },
  "directions": [ … ],         // 称呼与相处
  "groups": [ … ],             // 最多 6 个
  "stories": [ … ],            // 最多 60 个
  "memes": [ … ]               // 最多 30 个
}
```

`people`、`ratings`、`directions`、`groups`、`stories`、`memes` 可以整段不写（当作空）。其余字段一个都不能多、不能少，多写一个没见过的字段就是错误。

### 编号

- **已有角色**：用它的角色编号（导出的文件里能看到，例如 `role-3fa91c20`）。`validate` 无法知道服务器上有哪些角色，所以这里要你抄对；导入时服务器会逐一核对，不存在就报错并拒绝导入。
- **还不存在的角色**：写临时编号 `"new:<名字>"`，例如 `"new:林小满"`。文件里**所有**引用这个角色的地方（`characterId`、`ratings` 的两侧、`directions`、`groups.members`、`stories.participants`、`stories.overrides`、`memes.parties`）都写同一个 `new:…`。导入时服务器先建好角色草稿，再把它们全部换成真实编号。
  - `new:` 后面 1–40 个字，仅作临时标记；真正的名字取自 `identity.names[0]`。
  - **同一份文件导入两次不会建两个角色**：草稿里已经有一个第一个名字相同的角色，就认为是它。
- **人物**（`people`）要被引用，必须自己带编号，写成 `"new-<随便几个字母数字>"`，例如 `"new-owner"`；引用它的地方写同一个。导入后换成真实编号（同样按“第一个名字 + kind”避免重复）。
- **其余条目**（名字、别名、口头禅、经历、称呼与相处、组合、故事……）的 `id` 可以不写，服务器会分配并在以后保持不变。**不要自己编 `id`**：不在当前草稿里的 `id` 会被拒绝。从“导出文件”开始编辑时，已有条目的 `id` 原样留着即可，它们会被保留。

## 2. 每个字段与上限

字数按 JavaScript 字符串长度算（一个汉字 = 1）。标注“单行”的字段不能含换行，其余可以含换行。文本一律不能含控制字符。

### world
| 字段 | 上限 |
|---|---|
| `background` 世界背景 | 1000 |

### characters[]（聊天角色）
| 字段 | 上限 / 说明 |
|---|---|
| `characterId` | 已有编号，或 `new:…` |
| `workbench`（**仅新角色**，可选） | 见下文“角色工作台” |
| `identity.oneLiner` 一句话（单行） | 40 |
| `identity.names[]` 名字（单行） | 1–3 个，每个 ≤12。**第一个是主名**，别人的视图里都用它称呼他 |
| `identity.aliases[]` 别名 | ≤3 个：`text` ≤12（单行）、`attitude`: `likes` / `ok` / `dislikes`（他喜不喜欢被这样叫） |
| `identity.selfConcept` 自我认知 | 240 |
| `identity.prototype` | `null`，或 `{ "personId": 一个 kind 为 "prototype" 的人物, "inherited": ≤150, "notInherited": ≤150 }`（写清楚继承了什么、没继承什么） |
| `profile` 简介 | 800 |
| `personality` 性格 | 800 |
| `speech.catchphrases[]` 口头禅（单行） | ≤5 个，每个 ≤30 |
| `speech.samples[]` 说话样例（单行） | ≤5 个，每个 ≤100 |
| `speech.avoid[]` 不会这样说（单行） | ≤5 个，每个 ≤50 |
| `experiences[]` 经历 | ≤4 个：`title` ≤24（单行）、`text` ≤280 |
| `performance` 演绎说明 | 600 |
| `hidden[]` 不公开设定（单行） | ≤5 个，每个 ≤120 |
| `unmapped` | 6000。**留空 `""`**：这是旧资料转换时放“没处放的内容”的地方 |

### people[]（不是聊天角色的人）
| 字段 | 上限 / 说明 |
|---|---|
| `id` | 要被引用就写 `new-…` |
| `kind` | `person`（普通人）或 `prototype`（某个角色的原型） |
| `names[]`（单行） | 1–2 个，每个 ≤12 |
| `oneLiner`（单行） | 40 |

### ratings（单向评分）
`ratings["A"]["B"] = n`：**A 怎么看 B**。A 必须是聊天角色，B 是聊天角色或人物，不能是自己。`n` 是 **0 到 5，以 0.5 为一档**（`3`、`3.5` 可以，`3.3` 不行）。
**“没写”和 `0` 不一样**：没写 = 没设置（他对这个人没有看法），`0` = 他给了最低分。不确定就不要写。A→B 和 B→A 是两件事，各写各的。

### directions[]（称呼与相处）
`{ "from", "to", "address", "treatment" }`：**from 怎么称呼 / 怎么对待 to**。`from` 是聊天角色，`to` 是聊天角色或人物；同一个 (from, to) 只能有一条。

| 字段 | 上限 |
|---|---|
| `address` 称呼（单行） | 16 |
| `treatment` 相处 | 100 |

### groups[]（组合）
| 字段 | 上限 / 说明 |
|---|---|
| `name`（单行） | 1–20 |
| `members[]` | 聊天角色，≤15，不能重复，建议至少 2 个 |
| `background` 组合背景 | 120 |
| `stories[]` 组合故事 | ≤8 个，字段同下面的故事但**没有** `participants` / `overrides`；每个成员都算亲历 |

### stories[] 与 groups[].stories[]
| 字段 | 上限 / 说明 |
|---|---|
| `title`（单行） | 1–30 |
| `summary` 概要 | 200 |
| `details` 细节 | 500 |
| `period` | `{ "start": "", "end": "" }`：每个是 `""`、`YYYY`、`YYYY-MM` 或 `YYYY-MM-DD`；开始不能晚于结束；没有开始的故事按“最早”排 |
| `participants[]` | 聊天角色或人物，≤20，不能重复 |
| `boundary` 叙述边界 | 100 |
| `overrides[]` | ≤15 个 `{ "characterId", "level" }`，`level`: `lived`（亲历）/ `heard`（听说）/ `unknown`（不知道）；同一个角色只能一条 |

### memes[]（梗）
| 字段 | 上限 |
|---|---|
| `key`（单行） | 1–24 |
| `parties[]` | ≤8，聊天角色或人物 |
| `meaning` 含义 | 120 |
| `trigger` 何时用 | 100 |
| `prohibited` 禁忌 | 100 |

## 3. 谁知道哪个故事（知识规则）

对每个角色、每个故事，依次判断，**手动设置（overrides）永远优先**：

1. 他在 `participants` 里 → **亲历**：他的视图里有概要和细节。
2. 否则，他给任一参与者的评分 **≥ 3** → **听说**：他的视图里只有概要，没有细节。
3. 否则 → **不知道**：这个故事根本不出现在他的视图里。

组合故事：组合里每个成员都算亲历。所以评分要认真写：给谁打 3 分以上，就等于让他“听说”那个人的所有故事。

## 4. 不公开设定与叙述边界

- `hidden`：这个角色**知道、但绝不会直接说出口**的设定。只出现在他自己的视图里，并被标注为“不要直接说”；**不会**出现在任何别的角色的视图里。
- `performance`（演绎说明）、`speech.samples` 同样只给他自己，不进别人的视图。别的角色只能看到他的名字、别名、一句话。
- 每个故事的 `boundary`（叙述边界）告诉角色**可以怎样提起、不可以怎样编**这件事。亲历和听说的角色都会读到它。需要保护的事，同时写进 `hidden`（对当事人）和 `boundary`（对知情者）。

## 5. 上限一览

| 项目 | 上限 |
|---|---|
| 聊天角色 | 15 |
| 人物 | 40 |
| 整份阵容文档 | 300,000 字符 |
| **每个角色看到的视图** | **24,000 字符** |
| 请求体（导入文件） | 1,000,000 字节 |

视图 = 世界背景 + 他自己的全部内容 + 其他所有人的名片 + 他对每个人的评分与称呼相处 + 他的组合 + 他知道的故事 + 他是当事方的梗。超过 24,000 时，服务器按下面的顺序**舍弃**，直到放得下（他自己的内容、别人的名片、组合本身、评分永远不会被舍弃）：

1. 梗（排在后面的先走）
2. 听说的故事（最旧的先走；没有开始时间的算最旧）
3. 组合故事（最旧的先走）
4. 亲历的故事（最旧的先走）
5. 称呼与相处的文字（评分低的先走；评分本身保留）

`validate` 会列出每个角色的视图大小，以及超出时会被舍弃的故事标题。即使“会舍弃”也不算错误（舍弃是正常机制），但舍弃的往往是你写得最多的故事——大小接近上限时，先压缩，或者把不重要的故事去掉。只有“即使把所有可舍弃的都舍掉也放不下”才会让发布被挡住。

## 6. 完整内容写在阵容里，角色工作台只留一个短摘要

阵容开启后（`CAST_CONTEXT_ENABLED`），模型已经从阵容读到这个角色的全部内容。如果 角色工作台 的 人设 里再写一遍长篇设定，模型就会把同一个人读两遍，还可能前后不一致。所以：

- **完整的人物内容只写在阵容里**（`identity` / `profile` / `personality` / `speech` / `experiences` / `performance` / `hidden`）。
- 角色工作台 的 人设 保持一段**与阵容一致的短摘要**。
- 新角色可以在 `workbench` 里一次给齐这个短摘要（可选，每项都可省略，省略就用默认）：

```json
"workbench": {
  "displayName": "林小满",              // 显示名，≤12
  "persona": "十九岁的美术生，……",     // 短摘要，≤300
  "welcome": "嗨，我是小满。……"        // 欢迎语，≤200
}
```

  只有**新角色**（`new:…`）能带 `workbench`，它用来给新建的角色草稿填初始值。**已有角色的 角色工作台 资料永远不会被文件改动**，给已有角色写 `workbench` 只会得到一条“被忽略”的提醒。新角色的草稿仍然是草稿：不会上线、不能聊天，要在 角色工作台 里预演、批准、发布。

## 7. 虚构

所有角色都是**虚构人物**。不要写真实人物的私人信息（住址、电话、证件、真实关系、病史等），不要把真实事件当作事实写进故事。“原型”（`kind: "prototype"`）只借用公开、泛化的气质，并在 `inherited` / `notInherited` 里写明借了什么、没借什么。

## 8. 导入会做什么

- 文件**替换整份阵容草稿**：草稿里有、文件里没有的角色会被移出阵容（角色本身不会被删）。所以请从“导出文件”下载的当前草稿出发编辑，而不是从零写。
- 导入前，管理员会先看到摘要（新增 / 改动的角色、人物、评分、组合、故事数量，以及每个问题的位置和角色名），确认后才写入。
- 草稿修订号对不上（别人先改过）会被拒绝，重新选择文件即可。
- 导入是一个整体：新角色草稿、编号替换、草稿保存要么都成功，要么什么都没写。
- 它**不会发布**阵容，也不会发布任何角色。

## 9. 本地检查（validate）

```
node scripts/cast-file.ts validate cast.json
```

- 用的是服务器同一套规则（`apps/server/cast/cast-validation.ts`），每个问题打印为：`[错误] 角色名 · 路径 — 说明 (代码)`。
- `[发布会被挡住]`：能导入，但发布前必须处理。`[提醒]`：不影响任何事。
- 格式问题（多字段、类型不对、超长、超数量）**一次只报第一个**——修好再跑；含义问题（引用、评分、重复……）会一次列全。
- 它没有服务器上的数据，所以两件事只能到导入时才知道：已有角色的编号是否真实存在；文件里带的条目 `id` 是否是草稿发过的。
- 退出码：`0` 能导入且能发布；`1` 有问题；`2` 用法错误或读不到文件。
